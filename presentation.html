Community Health Screening Camp Scheduler

Problem Statement

Community health screening camps are coordinated through fragmented manual processes:

  • No centralized booking — patients call or walk in; paper registers at the venue
  • Overbooking and empty seats — no real-time capacity tracking
  • No automated reminders — high no-show rates, wasted capacity
  • Staff conflicts — doctors and volunteers double-booked across camps
  • No attendance data — no visibility into no-show rates or slot utilization

Today (Manual)

Phone/WhatsApp coordination · paper registers · no slot visibility · no reminders · no analytics

With CHSC

One web platform · real-time capacity · SMS/email reminders · QR check-in · live queue TV · analytics + CSV export

Proposed Solution

A centralized web platform with four role-based dashboards:

Patient Booking Portal

Discover camps → pick slot → confirm → QR pass → reminders (24h & 2h) → cancel/reschedule

Organizer Camp Management

Create camps, auto-generate slots, assign staff, monitor capacity and bookings

Doctor / Volunteer Camp Day

QR check-in, live waiting-room TV, attendance recording, no-show processing

Admin Governance

Analytics, capacity advisor, CSV export, user management, reminder audit log

Booking Concurrency — Zero Overbooking

How zero overbooking is guaranteed:

  1. Booking begins a transaction at READ COMMITTED isolation
  2. SELECT capacity, booked_count FROM slots WHERE id = ? FOR UPDATE acquires an exclusive X-lock
  3. Concurrent requests for the same slot block until the first transaction commits
  4. If booked_count < capacity: increment and insert booking; else join FIFO waitlist
  5. MySQL CHECK constraint booked_count <= capacity is the database backstop

Stress Test: 50 parallel bookings vs 10 seats

✓ Exactly 10 confirmed · 40 waitlisted (FIFO positions 1–40) · 0 overbooked · 0 server errors

Proof: backend/concurrency-test.js — runs against real MySQL InnoDB row locks.

Data Collection — 10 Categories (8 marks)

For every category we document: what, why, origin, validation, storage, usage.

Collected:

  • • Patient registration (name, phone, email, age group)

  • • Slot capacity (per-slot seats, booked count)

Also collected:

  • • Staff assignments (role, shift, load)
  • • Attendance records (check-in timestamps)
  • • No-show records (status transitions)
  • • Reminder delivery records (channel, provider, status)

Privacy: No medical history. DPDP-aligned erasure. All current data is seeded demonstration data.
